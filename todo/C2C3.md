# Bri Roadmap — Slices 1–12 (sequential autonomous execution, full scope)

## Mission

Twelve database-layer features for **Bri** (`bri-db`), to be delivered as an ordered sequence of independently-mergeable slices. Each slice ships with documentation and named E2E tests; the agent advances to the next slice only after the current one passes its acceptance criteria and merges cleanly.

**Domain boundary.** This work is pure database primitives — query planning, schema, vector index maintenance, graph algorithms, transactions, FTS, hooks, and worker offload. The agent must not introduce AI-specific concerns (embedding generation, ranking heuristics, prompt construction, policy thresholds, "what makes a good fact"). Those are caller responsibilities; Bri stays a generalised database whose users include but are not limited to AI applications.

**Sequencing rationale.** Slices are ordered to honor build dependencies (planner work before features that need it; cascade defaults before cascade hooks; WAL replay before time-travel reads) and to ship value to consumers early (range queries and polymorphic refs unblock the largest set of downstream callers).

**Scope discipline.** Anything achievable that adds value is in scope, regardless of effort. The only carve-outs are items that genuinely do not apply to Bri's single-machine local-database deployment model — distributed-across-machines, cross-process atomic coordination, multi-instance federation. Those are flagged "Not applicable to Bri's deployment model" with the reason; everything else lands as explicit acceptance criteria or documented API surface.

---

## Conventions the agent must honor (apply across every slice)

These are the existing developer-experience and economic patterns established by Bri V2.0.0. Deviations from them are breaking changes that must be flagged and justified explicitly.

1. **Chainable query builder.** New read primitives extend `db.get.{coll}S` chain methods (immutable per-link, thenable, terminal-aware). Each method returns a NEW builder with merged state. Method names cannot collide with the FROZEN reserved-names list in `engine/schema-edge-declare.js → RESERVED_PROXY_NAMES`. Adding a new reserved name is a major-version bump.
2. **Schema flags.** Per-collection metadata uses `$`-prefixed top-level keys (existing examples: `$edge`, `$indexes`, `$supersession`, `$confidence`, `$provenance`). New schema-level metadata follows the same convention. Field-level flags (existing example: `cascadeOn`) live inline on the field definition.
3. **Typed errors.** Throws use `BriValidationError`, `BriQueryError`, `BriProxyError`, `BriCascadeError` (or a sibling for the relevant subsystem) with a `code` enum. Each new error condition adds a documented code to the relevant errors module.
4. **Middleware chain order.** Writes flow through: schema validation → vector-index sync → secondary-index sync → graph-index sync → FTS-index sync → cascade-eligibility tagging. New middleware slots in at the appropriate position; do not reorder existing slots.
5. **Snapshot versioning.** Persistence changes that alter on-disk format bump the snapshot version. Readers handle older versions transparently and writers upgrade on the next snapshot trigger. v1/v2/v3 history is preserved in `docs/vector.md` §Persistence.
6. **Transaction participation.** Any new write surface participates in `db.rec()` / `db.fin()` / `db.nop()` / `db.pop()`. Pending state lives in a per-txn buffer; reads inside the txn see staged + committed; reads outside default to committed-only with `{txnId: null}` opt-out for explicit isolation testing.
7. **Observability.** Structured events emit through Bri's existing logger at the conventional levels (`INFO` for lifecycle, `DEBUG` for per-call detail, `WARN` for fallbacks, `ERROR` for crashes). Long-running operations emit progress events with bounded cardinality.
8. **Documentation deliverable per slice.** Each feature gets a dedicated `docs/<feature>.md` (or extends an existing doc) following the template established by `docs/vector.md`, `docs/graph.md`, `docs/cascade.md`: Quick start → API reference → How it works → Limitations → See also.
9. **Test deliverable per slice.** Each feature gets a named E2E test file at `tests/e2e/<feature>.test.js` (or extends an existing file when scope-aligned), with one `describe` block per acceptance criterion and at least one negative test (error code asserted).
10. **No new external dependencies.** Bri's stack stays pure-JS Bun-runnable. `BRI_*` env-var conventions are used for runtime toggles (existing: `BRI_ENCRYPTION_KEY`, `BRI_VECTOR_WORKER`, `BRI_VECTOR_RNG_SEED`, `BRI_DATA_DIR`, `BRI_MAX_MEMORY_MB`).
11. **Backwards compatibility.** Existing collections without the new schema flag, new option, or new chain method continue to behave identically. Collections that opt in get the new behavior. Default-behavior changes (Slice 8) require explicit migration notes in `docs/migration.md` and a CHANGELOG entry.
12. **Major-version discipline.** No major-version bump (`2.x → 3.0`) until all twelve slices are shipped or until the user explicitly requests a release. Each slice is a minor or patch release as appropriate.

## Slice 1 — Range queries on indexed fields (with multi-column range)

**Why.** The existing `SortedIndex` falls back to residual scan whenever a `.where()` clause uses an operator (`$gt`, `$gte`, `$lt`, `$lte`) on an indexed field. This is the foundational planner gap; downstream consumers running aggregation or filtered vector searches over large collections all benefit. Multi-column range — range on field A AND range on field B in the same query — is the natural extension and lands together so consumers don't have to re-architect twice.

**Deliverables.**
- `engine/sorted-index.js` (or equivalent) — extend with single-column range-scan support.
- `engine/multidim-index.js` (new, or extend existing index module) — multi-column range via composite-index-with-range-on-trailing-key OR a multi-dimensional index, whichever the engine prefers.
- `engine/query-planner.js` — pick the index when filter contains range clauses on indexed fields, including multi-column.
- `client/query-builder-residual.js` — when the index covers the range clause, the residual filter omits it (no double-evaluation).
- `docs/indexes.md` — extend with §Range queries (single-column and multi-column).
- `tests/e2e/secondary-index-range.test.js` — new file.

**API.** No new public surface. The existing `.where({field: {$gte: x, $lt: y}})` simply runs through the index when the field is in `$indexes`. Multi-column form: `.where({a: {$gte: x}, b: {$lte: y}})` uses a `[a, b]` composite index or a multi-dim index.

**Acceptance criteria.**
1. `SortedIndex` supports `$gt` / `$gte` / `$lt` / `$lte` and bounded ranges (`{$gt: a, $lte: b}`) with O(log N) lookup + O(matches) iteration.
2. The planner picks the index automatically — no caller hint required.
3. Mixed equality + range works: composite index `[['type', 'usage_count']]` covers `{type: 'fact', usage_count: {$gte: 8}}`.
4. **Multi-column range:** filters with range clauses on two or more indexed fields use the index for prefilter without falling back to scan. `[a, b]` composite index handles `{a: {$gte: x}, b: {$lte: y}}` sub-linearly.
5. Range on indexed field with non-indexed residual fields uses the index for prefilter; residual evaluates only on the candidate set.
6. `$in` on an indexed field continues to work (existing behavior preserved).
7. E2E benchmarks: 100k-row single-column range query completes in <50 ms p95 on a modest desktop; 100k-row multi-column range query completes in <100 ms p95.

## Slice 2 — Polymorphic ref-targets (full primitive unions)

**Why.** Edge collections sometimes need an endpoint that's *either* an entity reference *or* a primitive value. Today only single-collection refs work; consumers either declare parallel edge collections (fragmenting the graph) or stuff primitives into a separate field (fragmenting the schema). The full union solves it.

**Deliverables.**
- `engine/schema-registry.js` — accept primitive-union field types in validation.
- `engine/predicate-proxy.js` — return mixed arrays of hydrated entities + raw primitives on read.
- `engine/inverse-router.js` — handle polymorphic inverse (primitive targets have no inverse; multi-collection routes correctly).
- `engine/graph-index.js` — adjacency keys handle both `$ID`-typed and primitive-typed endpoints; primitive endpoints carry a type tag (`'string' | 'number' | 'date' | 'boolean'`) in the index entry.
- `docs/graph.md` — replace the v1 polymorphic-targets limitation with a §Polymorphic targets section.
- `tests/e2e/graph-polymorphic.test.js` — new file.

**API.**
```
db.schema('triple', {
  subject:    { type: 'ref',                          to: 'entity', required: true },
  predicate:  { type: String,                         required: true },
  object:     { type: 'ref|string|number|date|boolean', to: 'entity', required: true },
  $edge: { from: 'entity', to: 'entity', predicate: 'predicate', predicates: [...] }
});

const t1 = await alice.has_email('alice@example.com');     // string literal
const t2 = await alice.age(34);                            // number literal
const t3 = await alice.born_on(new Date('1990-01-01'));    // date literal
const t4 = await alice.is_admin(true);                     // boolean literal
const t5 = await alice.works_at(acme);                     // entity ref

const targets = await alice.related;
// Mixed: entities + strings + numbers + Dates + booleans. Consumer disambiguates by type.
```

**Acceptance criteria.**
1. Field types of the form `'ref|<primitive1>|<primitive2>...'` accept either a `$ID` matching the declared `to:` collection OR any of the named primitives (`string`, `number`, `date`, `boolean`). Per-document type-check runs in validation middleware; mismatched primitive throws `INVALID_POLYMORPHIC_PRIMITIVE_TYPE`.
2. `'a | b'` (two-collection polymorphism) accepts `$ID`s from either declared collection; inverse routing inspects the actual `$ID` prefix to pick the right collection.
3. Combined: `'ref|string'` with `to: 'a | b'` resolves entity refs against either of two collections, plus string literals — full union shape supported.
4. `await entity.{predicate}` returns mixed array; consumer differentiates via `typeof` + `instanceof Date` for the date case.
5. `await entity.{predicate}.$` returns full edge documents with the polymorphic field preserved as-is, with its primitive type intact (Date round-trips as Date, not as ISO string, via existing JSS serialization).
6. `entity.inverse.{predicate}` correctly handles polymorphism — primitive-typed targets have no inverse and are silently skipped (no throw, no phantom result).
7. `.expand({...})` traverses through ref endpoints; primitive endpoints are leaves (visited, budget-decremented, not expanded).
8. `.touching([seed])` matches on either polymorphic endpoint correctly — `$ID`-equality if seed is an entity, value-equality (with type-aware comparison for Date) if seed is a primitive.
9. Schema validation: declaring `'ref|...'` without `to:` throws `INVALID_POLYMORPHIC_REF_NO_TARGET`. Mixing types within a single document write succeeds; mixing across documents in the same collection succeeds.
10. E2E test: a `triple` collection with mixed object types (refs + every primitive) round-trips through write, read, predicate-proxy traversal, inverse, `.expand`, and `.touching`.

## Slice 3 — HNSW compaction (online + cross-collection)

**Why.** `docs/vector.md` line 213: tombstoned slots accumulate over deletion-heavy workloads, leaving dangling neighbour links that silently degrade recall. Compaction is database maintenance. Online incremental compaction means consumers never see whole-index pauses; cross-collection batched compaction means a single off-thread sweep handles everything that needs it.

**Deliverables.**
- `engine/vector-index-hnsw.js` — incremental compaction routine + trigger threshold check.
- `engine/vector-compactor.js` (new) — region-at-a-time online compaction; cross-collection scheduler that batches eligible collections into one off-thread sweep.
- `engine/vector-middleware.js` — emit progress events; participate in WAL.
- `engine/graph-algo.js` — new entries `db.algo.compactVectorIndex({collection})` and `db.algo.compactAllVectorIndices()` for manual triggers.
- New schema flag `$compactionThreshold` (default 0.25) declared inline on the vector field.
- `docs/vector.md` — add §Compaction section after §Persistence; remove the "ghost references" item from §Limitations.
- `tests/e2e/vector-compaction.test.js` — new file.

**API.**
```
db.schema('memoryArtifact', {
  embedding: { type: 'vector', dims: 1536, metric: 'cosine', $compactionThreshold: 0.25 }
});

// Manual trigger, single collection:
const r1 = await db.algo.compactVectorIndex({ collection: 'memoryArtifact' });
// → { tombstonesRemoved, vectorsCompacted, durationMs, mode: 'online' | 'whole-index' }

// Manual trigger, all eligible collections in one sweep:
const r2 = await db.algo.compactAllVectorIndices();
// → { byCollection: {<collection>: {...}}, totalDurationMs }
```

**Acceptance criteria.**
1. Compaction trigger fires automatically when tombstone density crosses the threshold; default 0.25 per-collection, configurable via `$compactionThreshold` schema flag.
2. **Online incremental mode (default).** Compaction runs region-by-region; foreground search on the rest of the index continues unaffected. Each region's compaction is atomic; mid-region crash recovers cleanly to pre-region state.
3. **Whole-index mode (opt-in).** `db.algo.compactVectorIndex({collection, mode: 'whole-index'})` runs a single full pass for cases where the consumer wants determinism; the operation reports progress and is interruptible.
4. **Cross-collection batched sweep.** `db.algo.compactAllVectorIndices()` walks every collection with a vector field, ranks by tombstone density, runs each in turn on the worker thread; report aggregates per-collection results.
5. Compaction runs on a background worker thread (or scheduled job slot); foreground search latency unaffected during compaction.
6. Idempotent — running twice in immediate succession is a no-op the second time.
7. After compaction completes, slot storage and HNSW topology produce within-1% recall against a fresh-from-survivors index over a fixed query set with known top-k truth.
8. Persistence: compaction state participates in WAL + snapshots. A crash mid-compaction recovers cleanly to either pre-compaction or post-compaction (or pre-region / post-region in online mode) — never a torn intermediate.
9. Observability: events `vector.compaction.start`, `vector.compaction.region.start`, `vector.compaction.region.complete`, `vector.compaction.progress` (every N vectors processed), `vector.compaction.complete`, `vector.compaction.error` emit at documented levels.
10. E2E tests: 10k vectors → 30% delete → recall drop measured → compaction → recall return to within 1%; cross-collection sweep across 3 collections completes in one logical operation; mid-region crash recovery test.

## Slice 4 — Object-form `.expand` edgeFilter (with lazy operators)

**Why.** `compileFilter` is the shared filter-spec compiler used by `.where` and `.having`. Allowing `.expand`'s `edgeFilter` to accept the same object form lets callers reuse a single filter spec across all surfaces. Adding lazy operators (`$elemMatch` for array fields, `$where`-with-callback for arbitrary predicates that can't be serialised) brings `.expand` to feature parity with `.where`.

**Deliverables.**
- `client/query-builder.js` — extend `.expand` to detect object-form `edgeFilter` and route through `compileFilter`.
- `engine/filter-compiler.js` — add `$elemMatch` and `$where` operator support; use across `.where`, `.having`, and the new `.expand` edgeFilter for parity.
- `docs/graph.md` — replace the v1 "function-form only" limitation with a §Filter shape note.
- `docs/aggregation.md` — extend §Filter operators with `$elemMatch` + `$where`.
- `tests/e2e/graph.test.js` and `tests/e2e/aggregation.test.js` — extend with object-form expand cases and lazy operators.

**API.**
```
const reach = await alice.expand({
  via: 'kgTriple',
  hops: 2,
  edgeFilter: {
    superseded_by_id: { $exists: false },
    confidence: { $gte: 0.8 },
    tags: { $elemMatch: { value: 'verified' } },
    $where: (e) => customPredicateThatCantBeSerialised(e)
  }
});
```

**Acceptance criteria.**
1. `edgeFilter` accepts either a function `(edge) => boolean` (existing behavior) or an object filter following the standard `compileFilter` operator vocabulary.
2. Object form is compiled at chain-build time (early validation of operator clauses); runtime evaluation produces identical traversal results to the equivalent function-form filter.
3. Function-form continues to work unchanged — backwards compatible.
4. **`$elemMatch`** matches array fields where any element satisfies a sub-filter object.
5. **`$where`** accepts a function value — used as a leaf predicate within an otherwise-object filter; cannot cross worker IPC (see Slice 11), throws `WHERE_CALLBACK_NOT_SERIALISABLE` if attempted in a worker context.
6. Mixed (one filter object + one filter function as siblings) is not supported; throws `EXPAND_FILTER_AMBIGUOUS` if both shapes are passed simultaneously at the top level.
7. The same operator set is available across `.where`, `.having`, and `.expand` — single source of truth.
8. E2E test: identical traversal results between object-form and function-form expressing the same filter; `$elemMatch` and `$where` work on both `.where` and `.expand`.

## Slice 5 — Numeric aggregations (full statistical surface)

**Why.** Calibration tooling — quick numeric summaries over filtered result sets. Today consumers pull the candidate set into JS and compute manually. Beyond the basic `.min` / `.max` / `.avg`, percentile / median / standard deviation / variance round out the statistical primitives, and weighted aggregations cover the common case of "score weighted by count."

**Deliverables.**
- `client/query-builder-terminals.js` — new terminals for the full aggregation set.
- `client/grouped-query-builder.js` — same surface for grouped aggregations.
- `engine/aggregation.js` (new or extension) — single-pass algorithms for percentile (P²-quantile estimator or sorted scan), stdev (Welford), weighted versions.
- `docs/aggregation.md` — extend §Terminals; rewrite §Limitations.
- `tests/e2e/aggregation-numeric.test.js` — new file.

**API.**
```
// Standard aggregations:
const lo  = await db.get.factS.min('score');
const hi  = await db.get.factS.max('score');
const avg = await db.get.factS.avg('confidence');
const sd  = await db.get.factS.stdev('confidence');
const v   = await db.get.factS.variance('confidence');

// Percentile + median:
const p90 = await db.get.factS.percentile('score', 0.9);
const med = await db.get.factS.median('score');                 // sugar for percentile(field, 0.5)

// Weighted aggregations:
const weightedAvg = await db.get.factS.avg('confidence', { weightedBy: 'usage_count' });
const weightedP50 = await db.get.factS.percentile('confidence', 0.5, { weightedBy: 'usage_count' });

// Grouped variants:
const byType = await db.get.factS.groupBy('type').stdev('confidence');
```

**Acceptance criteria.**
1. New terminals `.min(field)`, `.max(field)`, `.avg(field)`, `.stdev(field)`, `.variance(field)`, `.median(field)`, `.percentile(field, p)` on `QueryBuilder`; identical surface added to `GroupedQueryBuilder`.
2. `.where()` filter applies first; aggregation runs over the filtered set.
3. Operates on numeric fields only (Date treated as epoch-ms numeric for these aggregations); non-numeric values throw `AGGREGATE_NON_NUMERIC_FIELD` with offending document `$ID` in `details`.
4. Empty result set returns `null` for all (not `NaN`, not `0`).
5. **Weighted aggregations.** `.avg(field, {weightedBy: otherField})`, `.percentile(field, p, {weightedBy: ...})`, `.median(field, {weightedBy: ...})`. Weight field must be numeric ≥ 0; negative weights throw `AGGREGATE_NEGATIVE_WEIGHT`.
6. **Percentile algorithm.** P² estimator for streaming default; option `{exact: true}` runs a sorted scan for exact percentile when the candidate set is small enough (configurable threshold default 100k rows).
7. Single-pass `stdev` / `variance` use Welford's algorithm (numerically stable for large N).
8. Composes with `.having(filter)` after `.groupBy().percentile(...)` — `.having({percentile: {$gt: 0.85}})` works; `having` references the aggregate by its terminal name.
9. Index-aware short-circuit: when `.where()` covers an index AND the aggregated field is the index's sort key, `.min` / `.max` / `.median` (and `percentile` at `p ∈ {0, 1}`) read first/last entry instead of full scan.
10. Throws when combined with `.near` (parity with existing `.count` / `.distinct` semantics).
11. E2E tests: each terminal independently, weighted variants, grouped variants, exact-vs-streaming percentile parity at small N, index short-circuit cases.

## Slice 6 — Multi-key `.groupBy` (with computed-expression keys + rollup/cube)

**Why.** Many analyses need to group by combinations and computed expressions (e.g. `groupBy(['type', $dateTrunc('created_at', 'day')])`) and many reports need totals + subtotals + grand-totals in one query (rollup/cube/grouping-sets). Both are achievable extensions of the groupBy primitive and add substantial analytical value.

**Deliverables.**
- `client/query-builder.js` — extend `.groupBy()` to accept arrays + computed-expression objects.
- `client/grouped-query-builder.js` — generalise row shape; add `.rollup()`, `.cube()`, `.groupingSets()` modifiers.
- `engine/groupby-expressions.js` (new) — compile and evaluate computed expressions: `$dateTrunc`, `$stringPrefix`, `$bucketize`, `$identity` (pass-through), `$expr` (arbitrary callback for in-process callers).
- `engine/query-planner.js` — composite-index acceleration when index covers the groupBy key prefix; rollup/cube via in-memory aggregation tree.
- `docs/aggregation.md` — extend §Terminals; new §Computed-expression keys; new §Rollup, cube, grouping sets; remove multi-key + computed-expr items from §Limitations.
- `tests/e2e/aggregation-grouping.test.js` — new file.

**API.**
```
// Single-field (existing) and multi-field (new):
const byType   = await db.get.factS.groupBy('type').count();
const byTypeAndSession = await db.get.factS.groupBy(['type', 'source_session_id']).count();

// Computed-expression keys:
const byDay = await db.get.factS
  .groupBy([{ field: 'created_at', $dateTrunc: 'day' }])
  .count();
// → [{ created_at_day: '2026-05-01', count: 47 }, ...]

const byBucket = await db.get.factS
  .groupBy([{ field: 'confidence', $bucketize: [0, 0.5, 0.85, 1.0] }])
  .count();

// Rollup (totals + subtotals):
const sales = await db.get.salesS
  .groupBy(['region', 'product'])
  .sum('amount')
  .rollup();
// → rows for (region, product), then per-region subtotals, then grand total

// Cube (all combinations):
const cube = await db.get.salesS
  .groupBy(['region', 'product', 'quarter'])
  .sum('amount')
  .cube();

// Grouping sets (explicit):
const sets = await db.get.salesS
  .groupBy(['region', 'product'])
  .sum('amount')
  .groupingSets([['region'], ['product'], []]);
```

**Acceptance criteria.**
1. `.groupBy(['fieldA', 'fieldB', ...])` accepts an array of fields. Single-string form continues to work unchanged.
2. **Computed-expression keys.** Each array entry can be either a string (field name) or an object `{field, $<expression>: <args>}`. Built-in expressions: `$dateTrunc('day' | 'hour' | 'week' | 'month' | 'year')`, `$stringPrefix(n)`, `$bucketize([thresholds])`, `$identity`, `$expr((doc) => value)`.
3. Result row keys derived from computed expressions get a deterministic name: `<field>_<expression>` (e.g. `created_at_day`).
4. `.rollup()` modifier produces totals + per-prefix subtotals + grand total.
5. `.cube()` modifier produces all 2^n combinations of the groupBy keys.
6. `.groupingSets([[...], [...], ...])` produces explicit groupings; each inner array names the keys to group by for that set.
7. Subtotal rows in rollup/cube/groupingSets carry a `null` value (or sentinel — document the choice) in the columns they aggregate over; result shape is consistent across modes.
8. Composes with all aggregation terminals (`.count`, `.sum`, `.min`, `.max`, `.avg`, `.stdev`, `.variance`, `.median`, `.percentile`).
9. `.having(filter)` accepts predicates on the grouped fields, computed-expression-derived fields, AND the aggregated value.
10. Index-aware: composite indexes covering the groupBy keys (in declaration order) bound the candidate set without scan. Computed-expression keys that match an index's expression (e.g. an index on `$dateTrunc(created_at, 'day')`) accelerate.
11. Order of grouped fields in result rows is deterministic (preserved from the array argument order).
12. E2E tests: 2-key groupBy with count, 3-key with sum, computed expression (each built-in), rollup, cube, explicit groupingSets, having on aggregated row, composite-index acceleration.

## Slice 7 — Predicate chain method stacking (with cross-predicate)

**Why.** Today `.history`, `.confidence(t)`, and `.withProvenance` work as single terminals on a predicate accessor. Audit and inspection ergonomics require combinations: "show me superseded edges with confidence ≥ 0.8 that have provenance attached." Cross-predicate stacking via `entity.related` extends the same filter chain to every outgoing predicate at once.

**Deliverables.**
- `engine/predicate-proxy.js` — refactor `PredicateAccessor` so chain methods compose instead of terminating.
- `engine/predicate-proxy-filters.js` (new) — per-flag filter logic, applied as a single pass over edge candidates.
- `engine/related-accessor.js` — extend `.related` to accept the same chain methods, fanning out across every registered predicate.
- `docs/graph.md` — update §Predicate chain methods; remove the "stacking is v2" limitation; new §Cross-predicate stacking.
- `tests/e2e/graph.test.js` — extend with stacking and cross-predicate cases.

**API.**
```
// Single-predicate stacking:
const audit = await alice.works_at.history.confidence(0.8).withProvenance;
const auditEdges = await alice.works_at.history.confidence(0.8).$;

// Cross-predicate stacking (via .related):
const allFilteredAcrossPredicates = await alice.related.history.confidence(0.8);
// → array of targets across every outgoing predicate, filtered by the chain
const allFilteredEdges = await alice.related.history.confidence(0.8).$;
```

**Acceptance criteria.**
1. `entity.{predicate}.{chainA}.{chainB}.{chainC}` — any combination of `$supersession`-aware (`history`), `$confidence`-aware (`confidence(t)`), `$provenance`-aware (`withProvenance`) chain methods stack on a single predicate.
2. Order independence: `.confidence(t).history` produces identical results to `.history.confidence(t)`.
3. Terminal awaitable: `await entity.{predicate}.history.confidence(t)` returns the targets array; `.history.confidence(t).$` returns edge documents.
4. **Cross-predicate stacking.** `entity.related.{chainA}.{chainB}` applies the same chain to every outgoing predicate the schema registers; results unioned. `.$` works across predicates and returns edge documents from the appropriate edge collections (each tagged with its source predicate).
5. Filters applied in a single pass over edges (one walk of the index per predicate, not pipelined sequentially with re-fetches).
6. Schema validation: stacking a chain method whose required `$-flag` isn't declared on the predicate's edge collection throws `CHAIN_METHOD_NOT_AVAILABLE` at access time, with a diagnostic listing what's available.
7. Cross-predicate stacking gracefully handles heterogeneous predicates: predicates whose edge collections lack a given `$-flag` are skipped silently from that filter pass (or surfaced via a per-predicate report on the result, depending on engine choice — document the chosen behavior).
8. Stacks compose with `.limit(k)` — limit applied after the filter chain (per-predicate or globally; document the choice).
9. E2E tests: each two- and three-method stacking combination on a single predicate; cross-predicate stacking with mixed-`$-flag` predicates; `.limit(k)` interaction; `.$` edge-doc terminal interaction; negative test for missing `$-flag`.

## Slice 8 — Cross-collection atomic cascade (default-on)

**Why.** `docs/cascade.md` line 118 documents per-collection commits unless `{atomic: true}`. For any non-toy deployment, partial-cascade failure leaves the system inconsistent (half deletions, queries see torn views). v1 atomic-by-opt-in was acceptable; v2-grade default is atomic-by-default.

**Deliverables.**
- `engine/cascade.js` — flip default; opt-out via `{atomic: false}` for legacy callers.
- `engine/wal.js` — ensure cascade WAL records support transactional rollback across collections.
- `docs/cascade.md` — update §API, add §Migration note (opt-out for legacy behavior).
- `docs/migration.md` — add v2.x → v2.{next} note documenting the default change.
- `CHANGELOG.md` — explicit entry.
- `tests/e2e/cascade.test.js` — extend with mid-cascade failure scenarios.

**API.**
```
// New default: atomic across all eligible collections.
const result = await db.cascade.session('SESS_X');
// → { deleted, byCollection } — same shape; behavior is now all-or-nothing.

// Legacy per-collection commits:
const result = await db.cascade.session('SESS_X', { atomic: false });
```

**Acceptance criteria.**
1. Default `db.cascade.{scope}(id)` wraps the entire cascade across all eligible collections in a single transaction.
2. Backwards-compatible opt-out: `db.cascade.{scope}(id, {atomic: false})` for callers relying on per-collection commits.
3. WAL records ensure crash recovery applies the entire cascade or none of it. No partial states durable.
4. Error handling: a mid-cascade failure aborts the whole transaction; the thrown `BriCascadeError` includes which collection failed AND the byCollection map of how far the cascade got.
5. Performance: atomic cascade ≤ 2× slower than non-atomic over a 7-collection fixture (the typical real-world case). Document the budget in `docs/cascade.md`.
6. Documentation: V2.0.0 → V2.{next} default change is explicit in CHANGELOG with a migration note for callers relying on per-collection commits.
7. E2E tests: simulated mid-cascade failure leaves no partial state; success leaves no remaining matching records across all eligible collections; concurrent reads during cascade see either all-or-none state.

**Not applicable to Bri's deployment model.** Distributed cascade across separate Bri instances and cross-process atomic coordination remain out — Bri is a local-machine database and these concerns belong to the layer above (e.g. orchestration of multiple Bri instances).

## Slice 9 — Cascade hooks (whole + per-collection)

**Why.** Cascade is a single logical event but today consumers must subscribe to per-collection writes via pub/sub to react — clunky and racy on cascade ordering. Whole-cascade hooks let consumers reason about it as one event; per-collection cascade hooks let consumers react to a specific collection's deletions during a cascade without subscribing to all of them.

**Deliverables.**
- `engine/cascade.js` — fire `before:cascade` before the (atomic) cascade transaction begins; fire `after:cascade` after successful commit; fire `before:cascade:<collection>` and `after:cascade:<collection>` per collection within the cascade.
- `engine/event-bus.js` (or equivalent) — register the new event names.
- `docs/cascade.md` — add §Hooks section.
- `tests/e2e/cascade-hooks.test.js` — new file.

**API.**
```
// Whole-cascade hooks:
db.on('before:cascade', async ({ scope, id, collections, opts, txnId }) => { ... });
db.on('after:cascade',  async ({ scope, id, deleted, byCollection })    => { ... });

// Per-collection cascade hooks:
db.on('before:cascade:memoryArtifact', async ({ scope, id, txnId, willDeleteIds }) => { ... });
db.on('after:cascade:memoryArtifact',  async ({ scope, id, deletedIds })          => { ... });
```

**Acceptance criteria.**
1. New event names `before:cascade`, `after:cascade`, `before:cascade:<collection>`, `after:cascade:<collection>` registered alongside existing pub/sub events.
2. Event payload shapes: whole-cascade `before` carries `{scope, id, collections, opts, txnId?}`; whole-cascade `after` carries `{scope, id, deleted, byCollection}`. Per-collection `before` carries `{scope, id, txnId?, willDeleteIds}`; per-collection `after` carries `{scope, id, deletedIds}`.
3. `before:cascade` and `before:cascade:<collection>` hooks can throw to abort; the exception propagates and no documents are deleted. (Per-collection abort cancels the entire atomic cascade per Slice 8.)
4. `after:*` hooks fire only on successful commit. Hook errors in `after:*` are logged through Bri's logger but do not affect the cascade's commit (the deletion is durable; only the post-hook side-effect failed).
5. Async hooks awaited in registration order; serial execution by default.
6. Event-firing order during a cascade: whole `before:cascade` → for each collection (`before:cascade:<collection>` → deletes execute → `after:cascade:<collection>`) → whole `after:cascade`. Document this order; tests gate it.
7. Hook subscription failures dispatch on a separate error event so callers can monitor.
8. E2E tests: whole-cascade hooks fire with correct payload; per-collection hooks fire only for collections in scope; abort-via-throw on `before:` works at both levels; multi-hook ordering deterministic; `after:` failure doesn't roll back the cascade.

## Slice 10 — `.asOf(t)` point-in-time view (full temporal surface)

**Why.** Audit trail support — "what did the database know at time T?" — requires WAL-replay-bounded read at an arbitrary historical timestamp. Composes with all read primitives. Beyond reads, time-travel writes (branching from a historical state) and consistent isolation across collections at a past timestamp give the database real temporal capability rather than just a read-side audit feature.

**Deliverables.**
- `client/query-builder.js` — new chain prefix `.asOf(timestamp)` returning a time-bounded builder.
- `engine/wal.js` — add WAL-replay-up-to-timestamp primitive; schema-version awareness in replay.
- `engine/snapshot.js` — pick the most-recent-snapshot-before-timestamp as replay base; multi-collection consistent base.
- `engine/temporal-branch.js` (new) — fork-from-historical-state primitive for time-travel writes.
- `engine/schema-history.js` (new or extension) — per-snapshot schema record so historical replay applies the schema as it existed at the timestamp.
- `docs/asof.md` (new) — full temporal surface documentation.
- `docs/transactions.md` — add §Time-travel writes section.
- `tests/e2e/asof.test.js` — new file (read primitives).
- `tests/e2e/asof-write.test.js` — new file (time-travel writes + branching).
- `tests/e2e/asof-schema-migration.test.js` — new file (cross-schema-migration replay).

**API.**
```
// Read at a past timestamp (composes with all read primitives):
const past = await db.get.factS.asOf(new Date('2026-01-01')).where({ type: 'preference' });
const pastNeighbors = await db.get.factS.asOf(t).near(queryVec, 5);
const pastDegree    = await db.algo.degree({ collection: 'entity', via: 'kgTriple', asOf: t });

// Cross-collection consistent isolation at a past timestamp:
const snapshot = db.snapshot(t);                   // multi-collection consistent view
const past1 = await snapshot.get.factS.where(...);
const past2 = await snapshot.get.entityS.where(...);
// past1 and past2 reflect the same logical commit point

// Time-travel writes (branching from history):
const branch = db.branch.from(t, { name: 'what-if-no-Q3-correction' });
await branch.add.fact({ ... });                    // writes go to the branch
const branchedView = await branch.get.factS.where(...);
// Branches are isolated; merging back is explicit:
await db.branch.merge(branch, { strategy: 'overwrite' | 'reject-conflicts' | 'manual' });
```

**Acceptance criteria.**
1. **`.asOf(timestamp)`** chain prefix returns the collection's state as of `timestamp` (Date or epoch-ms accepted).
2. Composes with `.where`, `.match`, `.near`, `.expand`, `.chain.{field}`, `.touching`, `.between`, all aggregations, and `entity.{predicate}` (when accessed via `.asOf`-rooted entities).
3. Read-only on the default `db.get.{coll}S.asOf(...)` path — `.save()` on `.asOf()` results throws `ASOF_RESULT_READONLY`.
4. WAL replay from most-recent-snapshot-before-timestamp up to the timestamp; bounded by the snapshot interval. Worst case documented.
5. **Cross-collection consistent isolation.** `db.snapshot(t)` returns a snapshot handle scoped to `t`; multiple reads through the handle observe the same coherent state across collections (consistent across the whole database, not just per-collection).
6. **Cross-schema-migration replay.** WAL records carry the schema version active when they were written; replay applies the historical schema correctly so an asOf-read against a pre-migration timestamp returns documents with their pre-migration shape (where field renames or removals affected the field set).
7. **Time-travel writes via branching.** `db.branch.from(t)` creates a named fork; writes against the branch handle do not affect the main timeline. Branches persist in WAL until merged or discarded.
8. **Branch merge.** `db.branch.merge(branch, {strategy})` applies the branch's writes back to the main timeline. Strategies: `overwrite` (branch wins), `reject-conflicts` (any conflict aborts), `manual` (returns conflict list, caller resolves doc-by-doc).
9. **Branch discard.** `db.branch.discard(branch)` deletes the branch's WAL entries; main timeline unaffected.
10. `db.algo.{name}` extends to accept `asOf:` option for time-bounded algorithm runs (`degree`, `expand`, `compactVectorIndex`, `ppr` once it lands per separate roadmap).
11. Edge cases: timestamps before any data (returns empty), timestamps after current state (returns current). Branches fork from a state with NO future writes from the main timeline applied (clean fork point semantics).
12. E2E tests: write at known times → time-travel read → verify edits between returned-state and now don't appear; multi-collection consistent snapshot test; cross-schema-migration replay (a renamed field reads correctly under both old and new names depending on `t`); time-travel write to a branch → merge with each strategy; branch discard.

## Slice 11 — Worker-thread query path (multi-worker + zero-copy IPC)

**Why.** `.near()` queries today execute in-process because filter predicates are arbitrary JS that can't cross the worker IPC barrier. At scale (100k+ vectors, concurrent queries), this blocks the event loop. Object-form filters (after Slice 4) can be serialised. Multi-worker per-query parallelism splits a large top-k across N workers and merges. SharedArrayBuffer zero-copy IPC removes the serialisation cost on hot paths.

**Deliverables.**
- `workers/vector-query-worker.js` — new worker that runs `.near()` with object-form filters and returns top-k IDs + scores.
- `workers/vector-query-pool.js` — pool manager (size N, queue, dispatch).
- `client/query-builder-vector-exec.js` — detect object-form filter + worker enabled → route to worker; function-form → fall back to in-process.
- `engine/vector-index-hnsw.js` — expose worker-friendly read interface; SharedArrayBuffer-backed slot-storage view for zero-copy.
- `engine/vector-index-shared-buffer.js` (new) — SharedArrayBuffer wrapper, lock-free reads, copy-on-write semantics for the index buffer.
- New env-vars `BRI_VECTOR_WORKER_QUERY` (whitelist same as `BRI_VECTOR_WORKER`) and `BRI_VECTOR_WORKER_POOL_SIZE` (integer, default 1).
- `docs/vector.md` — add §Worker-thread query path; add §Multi-worker parallelism; add §SharedArrayBuffer zero-copy IPC; update §Limitations.
- `tests/e2e/vector-worker-query.test.js` — new file.

**API.**
```
// Per-call opt-in:
const results = await db.get.factS
  .where({ type: 'a' })
  .near(queryVec, 20, { worker: true });

// Multi-worker per-query parallelism (large k):
const big = await db.get.factS
  .near(queryVec, 200, { worker: true, parallelism: 4 });
// → split top-k across 4 workers, merged top-200

// Process-wide via env-var:
// BRI_VECTOR_WORKER_QUERY=true
// BRI_VECTOR_WORKER_POOL_SIZE=4
```

**Acceptance criteria.**
1. `BRI_VECTOR_WORKER_QUERY=true` (whitelist `true`/`1`/`yes`/`on`; disable via `0`/`false`/`no`/`off`) enables process-wide; per-call `{worker: true}` overrides per-query.
2. **Object-form filter routing.** `.where(filter)` with object-form filters compiled by `compileFilter` execute in the worker; function-form falls back to in-process with a typed warning event `vector.worker.fallback.functionFilter`.
3. Result hydration on the main thread (so reactive entity behavior is preserved post-search).
4. Latency: worker query path adds <5 ms overhead on small queries (k=10 over 1k vectors); net-positive on large queries (k=20 over 100k vectors). Benchmark documented.
5. **Worker pool.** Configurable size via `BRI_VECTOR_WORKER_POOL_SIZE` env-var or `db.configure({ vectorWorkerPoolSize: N })`. Pool shared across all collections; queries queue when all workers busy.
6. **Multi-worker per-query parallelism.** `{worker: true, parallelism: N}` splits the top-k computation across N workers (each searching a partition of the index or running an independent search with merging on the main thread); document the chosen partition strategy.
7. **SharedArrayBuffer zero-copy IPC.** The slot-storage Float32Array is held in a SharedArrayBuffer when the worker pool is active; workers read directly without copy. Writes use copy-on-write so concurrent readers see a consistent index without locks. Falls back to structured-clone copy if SharedArrayBuffer is unavailable in the runtime (e.g. without cross-origin isolation in browser embeds).
8. Crash isolation: a worker crash recovers by spawning a fresh worker; in-flight queries fail with `BriQueryError { code: 'VECTOR_WORKER_CRASHED' }` and the caller can retry. Pool integrity preserved (other workers unaffected).
9. Observability: events `vector.worker.query.start`, `vector.worker.query.complete`, `vector.worker.query.queue-depth`, `vector.worker.crash`, `vector.worker.fallback.*`, `vector.worker.parallel.split`, `vector.worker.parallel.merge` emit at documented levels.
10. E2E tests: object-form filters in worker; function-form fallback works; concurrent queries don't block; worker crash + recovery; multi-worker split + merge produces same top-k as single-worker for the same query; SharedArrayBuffer fast path vs structured-clone fallback parity.

**Not applicable to Bri's deployment model.** Distributed workers across machines are not in scope — Bri is single-machine; cross-machine search belongs to the layer above (e.g. shard router across multiple Bri instances).

## Slice 12 — Production-grade FTS (BM25 + phonetic + fuzzy + language detection + custom analyzers)

**Why.** v1 substring `.match()` is correct but degrades on word stems, stop-words, multi-word phrases, and collection scale. Persistent inverted index + BM25 is standard production FTS; phonetic matching catches misspellings and name variants; fuzzy match catches typos; language detection auto-picks stemmer/stopwords for mixed-language corpora; custom analyzer pipelines let advanced consumers compose tokenize → stem → stopword → custom-filter chains.

**Deliverables.**
- `engine/fts-index.js` — new persistent inverted-index data structure.
- `engine/tokenizer.js` — pluggable tokenizer (default: whitespace + punctuation, case-folded).
- `engine/stemmer.js` — Porter stemmer + extensible language registry.
- `engine/stopwords.js` — language-specific stopword lists.
- `engine/bm25.js` — BM25 ranking.
- `engine/phonetic.js` — Soundex, Metaphone, Double Metaphone encoders.
- `engine/fuzzy.js` — Levenshtein distance + BK-tree index for sub-linear fuzzy lookup.
- `engine/language-detect.js` — pure-JS n-gram-based language detector with confidence threshold.
- `engine/analyzer-pipeline.js` — composable pipeline: array of stages, each a function `(tokens) => tokens`.
- `client/query-builder.js` — extend `.match()` with options OR add new `.search(query, opts)` chain method (see API below).
- New schema flag `$fts: { ... }` declares per-collection FTS config.
- Snapshot version bump for persisted FTS index.
- `docs/fts.md` — major rewrite: every sub-section.
- `docs/migration.md` — note about opting collections in.
- `CHANGELOG.md`.
- `tests/e2e/fts.test.js` — major extension (likely renamed from `match.test.js`).
- `tests/e2e/fts-phonetic.test.js`, `tests/e2e/fts-fuzzy.test.js`, `tests/e2e/fts-language.test.js`, `tests/e2e/fts-analyzer.test.js` — new files for each new capability.

**API.**
```
db.schema('chatTurn', {
  content: { type: String, required: true },
  $fts: {
    tokenize:  'default',                                        // or custom function name
    stem:      'en',                                             // or 'auto', or false
    stopwords: 'en',                                             // or 'auto', or [array]
    phonetic:  'metaphone',                                      // or 'soundex' or false
    language:  'auto',                                           // 'auto' = detect per-doc
    analyzer:  ['tokenize', 'lowercase', 'stem', 'stopword',     // pipeline composition
                { custom: 'stripDiacritics' }]
  }
});

await db.add.chatTurn({ content: 'Encrypted gateway design notes' });

// BM25 search:
const hits = await db.get.chatTurnS.search('encrypt');                       // stem matches "encrypted"
for (const hit of hits) console.log(hit.$ID, hit.$bm25, hit.$matchHits);

// Phrase:
const phrase = await db.get.chatTurnS.search('"API gateway"', { phrase: true });

// Phonetic match (catches "Smith" / "Smyth" / "Smithe"):
const sound = await db.get.personS.search('Smith', { phonetic: true });

// Fuzzy match (Levenshtein distance ≤ 2):
const fuzzy = await db.get.chatTurnS.search('encryption', { fuzzy: 2 });

// Combined:
const everything = await db.get.chatTurnS.search('encrypt', {
  phonetic: true,
  fuzzy: 1,
  phrase: false
});

// Backwards-compatible: collections without $fts still use substring .match().
const substr = await db.get.chatTurnS.match({ content: 'gateway' });

// Custom analyzer pipeline (via $fts.analyzer with a custom-named stage):
db.registerAnalyzerStage('stripDiacritics', (tokens) => tokens.map(stripDiacritics));
```

**Acceptance criteria.**
1. New chain method `.search(query, options?)` runs BM25-ranked retrieval against the persistent inverted index. (Existing `.match()` continues to work as substring scan for collections without `$fts` declared — backwards compatible.)
2. **Tokenization.** Default: whitespace + punctuation split, case-folded. Pluggable via `$fts.tokenize` flag with documented presets and custom-function registration.
3. **Stemming.** Porter stemmer for English by default; pluggable per language via `$fts.stem`; setting `stem: 'auto'` triggers per-document language detection (see below).
4. **Stopwords.** Language-specific lists (`$fts.stopwords: 'en'`); `'auto'` triggers detection; `[array]` for explicit custom lists.
5. **BM25 ranking** replaces binary match-score; each result carries non-enumerable `$bm25` (the score) and `$matchHits` (matched-term metadata + positions).
6. **Multi-word phrase.** `{phrase: true}` treats the query as an exact phrase (term positions checked).
7. **Phonetic matching.** `$fts.phonetic: 'soundex' | 'metaphone' | 'doubleMetaphone'` builds a parallel phonetic index; `.search(query, {phonetic: true})` matches phonetically. Combinable with stemming.
8. **Fuzzy match.** `.search(query, {fuzzy: N})` allows up to N edits via Levenshtein over a BK-tree index. Sub-linear lookup; performance characterised in `docs/fts.md`.
9. **Language detection.** `$fts.language: 'auto'` uses pure-JS n-gram detector to pick stemmer/stopwords per document at index time (with confidence threshold; below threshold falls back to a configured default). Per-document detected language is stored in the index for query-time matching.
10. **Custom analyzer pipelines.** `$fts.analyzer` is an array of stage names (built-ins) and `{custom: <name>}` references. Custom stages are registered via `db.registerAnalyzerStage(name, fn)`. Pipeline composes left-to-right; each stage transforms a token stream.
11. **Persistent inverted index.** Built incrementally on writes, persisted in snapshots (snapshot version bump), recoverable from WAL.
12. Index updates participate in transactions: writes inside `db.rec()` visible to in-txn `.search()`; outside-txn `.search()` sees committed-only.
13. Eventual consistency outside transactions acceptable (within ~1 s of write); inline `.match()` continues to provide strict-consistency substring matching.
14. Composes with `.where()` prefilter (secondary-index narrowing keeps hydration bounded).
15. **Index-rebuild migration helper.** `db.algo.rebuildFtsIndex({collection})` for schema-flag-added-after-data; `{partial: ['phonetic' | 'fuzzy' | 'main']}` for selective rebuild.
16. Observability: events `fts.index.update`, `fts.index.rebuild.start`, `fts.index.rebuild.complete`, `fts.language.detect.confidence`, `fts.fuzzy.tree.depth`.
17. E2E tests: stemming match, stopword filtering, multi-word ranking, BM25 vs naive scoring, transactional isolation, snapshot persistence, rebuild migration, phonetic matching against name variants, fuzzy matching with deliberate typos, language detection on a multi-language fixture, custom analyzer pipeline composition.
